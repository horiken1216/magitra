# 調査記録（2026-11-16〜）

開発中に実機で調べたこと・試したことの記録。日付順に追記している（「ユーザー確認」は開発者が実機で体感して確かめたもの）。

## デバイス
- Magic Trackpad（Lightning、2021 年の第 3 世代）、PID 0x0265
  - BT の表示名・HID の製品名はどちらも「Magic Trackpad」（「2」が付かない）。
    PID 0x0265 は 2015 年の Magic Trackpad 2 と共通なので、PID だけでは区別できない
  - 当初は PID と Linux の呼び名から「Magic Trackpad 2」と書いていた。2026-11-16 に呼び名を改めた
- BT: VID 0x004C（BTHENUM / hidbth 経由）
- USB: VID 0x05AC（充電専用ケーブルでは認識されなかった。データ通信用ケーブルでの結果は「USB 接続時」）
- USB-C の第 4 世代（PID 0x0324）は手元になく、未確認（docs/INSTALL.md「対応機種」）

## BT 接続時に Windows が公開している HID コレクション
| コレクション | Usage | 入力 | 出力 | フィーチャー | 備考 |
|---|---|---|---|---|---|
| Col01 | 0x0001/0x0002 (Mouse) | 0x02 (8B) | なし | 0x55 (65B) | OS が専有。アプリから開くと err=5 |
| Col02 | 0xFF00/0x0014 | 0x90 (3B) | なし | なし | ベンダー定義。おそらくバッテリー |

## 検証結果
- Col02 へ `F1 02 01`（BT マルチタッチ有効化）と `02 01`（USB 用）を HidD_SetFeature → どちらも ERROR_INVALID_FUNCTION (1)
- 記述子にない Report ID は hidclass が送受信の前に弾く。マルチタッチ用の入力 0x31 も記述子にないため、届いても破棄される
- 10 秒間触っても Col02 に入力レポートは届かなかった

## 結論
BT 接続でマルチタッチ・圧力の生データを得るには、hidclass より下に入るフィルタードライバーが必要。
そのドライバーで次の2つを行う。

1. 有効化レポートを送り、マルチタッチモードへ切り替える
2. 記述子を書き換え、レポート 0x31 を Windows に届く形へ変換する

ユーザーモードだけでは実現できない。

## USB 接続時（2026-11-16 追記）

USB Composite Device（`USB\VID_05AC&PID_0265`）の下に 4 インターフェイス。どれも hidusb で動いている。

| IF | コレクション | Usage | 入力 | 出力 | 備考 |
|---|---|---|---|---|---|
| MI_00 | Col01 | 0xFF00/0x0B | 0x9A, 0xE0 (5B) | - | Device Management |
| MI_00 | Col02 | 0xFF00/0x14 | 0x90 (3B) | - | おそらくバッテリー |
| MI_01 | Col01 | 0x0001/0x0002 (Mouse) | 0x02 (8B) | - | OS が専有（err=5） |
| MI_01 | Col02 | 0x000D/0x0005 (Touch Pad) | 0x3F (17B) | - | フィーチャーなし。PTP の必須要件を満たさない |
| MI_01 | Col03 | 0xFF00/0x0C | 0x44 (**1388B**) | - | マルチタッチ生フレームの可能性 |
| MI_02 | - | 0xFF00/0x0D (Actuator) | 0x3F (16B) | **0x53 (64B)** | ハプティクス制御の可能性。未検証 |
| MI_03 | - | 0xFF00/0x03 (Accelerometer) | 0xC0 (108B) | - | |

- マウス以外の 6 コレクションはアプリから開ける。しかし 15 秒触っても入力レポートは 1 件も届かない（既定モードでは入力がマウス用 0x02 にしか流れないと見られる）
- `02 01` / `02 01 00 00` の HidD_SetFeature は全コレクションで ERROR_INVALID_FUNCTION (1)。記述子にフィーチャー 0x02 がない
- 結論: USB でも、標準 HID スタックの上からはマルチタッチモードへ切り替えられない。
  署名なしで進めるなら、MI_01 に Microsoft 署名済みの WinUSB を当て、制御転送で切り替え・割り込みエンドポイントを直接読む方式（方式 B）になる

## 方式 B（WinUSB）での実機検証（2026-11-16）

- `pnputil /add-driver ... /install` で MI_01 に WinUSB が入った（oem23.inf）。**テスト署名モードなし**、カタログの自己署名とローカル信頼だけで導入できた
- MI_01 は interrupt IN パイプ 0x83（maxpacket 64、interval 1）が 1 本
- 既定モード: ID 0x02、8 バイトのマウス用レポートだけが流れる
- `SET_REPORT`（Feature、ID 0x02、`02 01`、wIndex = 1）でマルチタッチモードに切り替わる。以降は長さ 12 + 9n（n = 1〜5 を確認）のフレーム
- 解析結果（486 接触点）
  - X: -3341〜684、Y: -891〜1889（想定範囲内）
  - 圧力: 触れているだけで平均 11.9、押し込み中は平均 170.5（最大 220）。Force Touch の判定に使える
  - ID は指が離れるまで不変
  - 状態ビット（byte3 上位 2bit）: 1 = 触れ始め、2 = 接触中、0/3 = 離れる途中（接触サイズ・圧力 0）。0 と 3 の違いは未確定
  - ヘッダーの byte 8〜11 はフレームごとに変化（タイムスタンプと推定）
- 記録した 2 フレームを `core/tests/test_report.c` の回帰テストに採用
- Y 軸の向き: 指データの 13bit 値を符号反転した Y は**下（手前）が正**（画面座標と同じ）。
  当初「上が正」と誤記していた。Linux hid-magicmouse と imbushuo のドライバーの扱い、
  および mtpagent の記録（奥へ動かした区間で Y が -983 → -1963 に減少）で訂正した
- 触れている間のフレーム頻度: 約 89〜90 フレーム/秒（間隔 平均 11.1ms、最大 22ms）

## ハプティクス（Actuator, USB MI_02）の調査（2026-11-16）

- MI_02 は標準 HID（hidusb）のまま。アプリから開ける
- 記述子（38 バイト）: `06 00 ff 09 0d a1 01 85 3f 09 0d 15 00 26 ff 00 75 08 95 0f 81 02 85 53 09 0d 15 00 26 ff 00 75 08 95 3f 91 02 c0`
  - 入力 0x3F: 15 バイト、出力 0x53: 63 バイト。どちらも Usage 0xFF00/0x0D の不透明なバイト列。フィーチャーレポートはない
- 入力 0x3F は 12 秒間の観察で 0 件（自発的には送られないか、観察時に触れていなかった）
- 公開情報（一次資料で確認したもの）
  - imbushuo の gist（USB, PID 0x0265, MI_02 対象）: `53 01 15 6C 02 00 21 2B 06 01 00 16 41 13` を書くと振動する。
    `53 01` が固定値、続く 4 バイトが強さ（uint32）、残りは不明（作者いわく 0 でもよい）。速すぎる書き込みは拒否される
    https://gist.github.com/imbushuo/2d18a9e6f771d0055223a78930a9171c
  - MagicTrackpad2ForWindows PR #63: BT 版 `F2 53 01 s0 78 02 s1 24 30 06 01 s2 18 48 12`（s0/s1/s2 が強さ）。USB 版は実機未検証で PR は閉じられた
    https://github.com/vitoplantamura/MagicTrackpad2ForWindows/pull/63
  - LinuxMagicForce: s1 は 0x20 以下、s2 は 0x40 以下に抑えるよう警告（超える値は「ハードウェアに負荷をかける実験的な設定」）
  - クリックの強さ・無音クリックの永続設定はフィーチャー 0x22/0x23 という報告あり（nexustar/linux-hid-magicmouse、linux-input のパッチ）。
    この PC の MI_02 記述子にはフィーチャーがないため、標準 HID 経由では送れない
- 試験: gist のバイト列を 64 バイトに 0 埋めして `hid.write` で送信（`probe/actuate.py`）。2 回送り、どちらも 64 バイト書き込み成功。
  **ユーザーが振動を体感した**（「一回振動した」）。ドライバー変更なし、標準 HID の出力レポートでハプティクスを鳴らせる。
  2 回のうち 1 回だけ感じたのか、毎回鳴るのかは未確認（次回、回数を指定して確認する）
- 再現性: 予告して準備してもらったうえで、gist の値を 1.5 秒おきに 3 回送信 → **3 回とも振動を体感**。送るたびに確実に鳴る
- 強さの試験（強さ以外は gist の値に固定、上限 s0 <= 0x30、s1 <= 0x20、s2 <= 0x40）
  - PR #63 のプリセット 弱(15,04,04)・中(17,06,06)・強(1E,08,08) を 3 秒おきに送信 → **違いが分からない**（差が小さすぎると推定）
  - 1 バイトずつ上限まで上げて基準 (15,00,00) と比較（1 組ずつ予告して実施）
    - 組 A: s0 0x15 → 0x30 → **強くなった**。USB でも s0 は強さに効く
    - 組 B: s1 0x00 → 0x20（s0 は基準のまま）→ **質が変わった**。USB でも s1 は振動の質に効く（具体的な変化は未聴取）
    - 組 C: s2 0x00 → 0x40（s0/s1 は基準のまま）→ **重くなった**
  - 結論: USB（PID 0x0265, MI_02）では s0 = 強さ、s1 = 鋭さ（質）、s2 = 深さ（重さ）がそれぞれ独立に効く。
    公開プリセットは差が小さく、体感では区別できなかった。`core/` の `MtpBuildActuatorReport` に上限付きで実装

## Force Touch の判定（2026-11-16）

- 押し込み中の圧力（mtpagent-cli --log で記録）
  - 普通のクリック（すぐ離す）: 最大 148〜156、中央値 118〜138
  - 強い押し込み: 押し始めから 1〜2 フレーム（2〜34ms）で 200 を超え、上限 253 に張り付く
  - **普通に押したままのドラッグでも、途中で 253 まで上がることがある**（5 フレーム目で 200 超え）
  - ボタン（btn）は押している間ずっと 1 のまま（1.3〜3.8 秒の長押しで確認）
- このため、圧力だけでは「強い押し込み」と「押したままのドラッグ」を区別できない。
  判定は押し始めの約 0.15 秒（14 フレーム）に限り、その間に約 2mm（100 単位）動いたらドラッグとして扱う（agent/mtp_gesture.c）
- 実機の記録を判定に流し直して確認（agent/tests/replay_gesture.c）: 普通のクリック 3 回・強い押し込み 3 回を正しく区別、
  実使用 30 秒の記録で誤発動なし、圧力 253 のドラッグも左ボタンとして扱った
- 体感での確認: 強い押し込み 3 回で、振動を送った回数（3 回）と、ユーザーが感じた重い振動の回数（3 回）が一致
  - トラックパッド本体も押した・離したときに「カチッ」と振動するため、回数を数えるときは区別が必要
- 実使用（入力を送る 30 秒）: ブラウザのリンクの上で強く押し込むと新しいタブで開いた（中クリック）。
  普通のクリックの遅れ（最大 0.15 秒）は気にならないとのこと。左クリック 5 組・Force Touch 2 回、送信の失敗なし
  - 1 回だけフレーム間隔が 212ms 空いた（普段は約 11ms）。原因は未調査

## 管理者権限のウィンドウへの入力（UIAccess、2026-11-16）

- 普通の mtpagent.exe（Medium）からの SendInput は、管理者権限のウィンドウ（タスクマネージャーなど）に届かない（UIPI）
- UIAccess 版（マニフェスト `level="asInvoker" uiAccess="true"`）を自己署名証明書で署名し、`C:\Program Files\MTP` に置いて起動
  - tools\manual-install\check_uiaccess.ps1 の結果: uiAccess = True、elevated = False、整合性レベル High
  - **タスクマネージャーの中でクリックとスクロールが効いた**（ユーザー確認）
- 証明書について分かったこと
  - 手順 3（証明書を「信頼されたルート」に登録）をしないまま、WinUSB の INF は導入できていた（ドライバー本体が Microsoft 署名のため）
  - UIAccess には「信頼されたルート」への登録が必須（install.ps1 が事前に確かめる）
  - 16:47 に作った証明書が、秘密鍵ごとユーザーの証明書ストアから消えていた（理由は不明。会社の管理ツールの可能性）。
    作り直して署名・導入した。署名は実行ファイルに埋め込まれるので、導入後に秘密鍵が消えても、信頼の登録が残っていれば動く

## インストーラー（mtpsetup.exe、2026-11-16）

- 一般の PC には signtool がないため、Windows 標準の Set-AuthenticodeSignature で署名する。
  一時証明書でカタログ（.cat）と実行ファイル（.exe）の両方に署名できることを確認した
- ユーザーが UIAccess 版の導入 → 取り除く、を実行。取り除いた後は、MI_01 が標準の HidUsb（マウスは mouhid）に戻り、
  C:\Program Files\MTP・導入の記録・MTP の証明書（手作業の MTP Test Signing を含む）・ドライバーパッケージが残っていないことを確認
- 作り直したインストーラーで UIAccess 版を再導入: 常駐アプリは uiAccess = True・昇格なしで起動、信頼されたルートには
  「MTP Local Signing」（秘密鍵なし）だけ、PC の証明書ストアに秘密鍵つきの証明書は残っていない、MI_01 は WINUSB、
  「アプリ」の一覧に登録済み
- 同意画面で「UIAccess 版を選んだのに標準版（WinUSB）の説明が出る」と受け取られた。WinUSB は両方の版に共通なので、
  「選んだ版」と「どちらの版でも行うこと / UIAccess 版だけで行うこと」に分けて表示するよう直した

## ロック中・ログオン前の標準 HID への切り替え（MtpSwitch サービス、2026-11-16）

- UpdateDriverForPlugAndPlayDevices で MI_01 を input.inf（HidUsb）と MtpUsb.inf（WINUSB）の間で切り替える
- **落とし穴: 常駐アプリが WinUSB のハンドルを開いたままだと、切り替えは「登録だけ」で終わる**
  - PnP が機器を止められず、SPDRP_SERVICE は HidUsb になるが、DevNodeStatus に DN_NEED_RESTART が立ち
    （DEVPKEY_Device_IsRebootRequired = True）、機器は WinUSB で動き続ける。HID の子（mouhid のマウス）も現れない
  - 戻り値の「再起動が必要」= 1 は、この状態を正しく伝えていた。約 8 秒かかっていたのも、止めようとして待たされた時間
  - この状態でもポインターが動いたのは、常駐アプリが入力を送っていたから。ロック画面でクリックすると
    入力欄（セキュリティ保護されたデスクトップ）に移り、そこには送れないので動かなくなった
  - Kernel-PnP の 411（0xC00000E5）は、成功した切り替えでも毎回出るので、判断材料にならない
- 対策
  - 常駐アプリ: WM_WTSSESSION_CHANGE でロック・切断時にハンドルを閉じ、解除時に開き直す
  - mtp_switch: サービス名に加えて DN_NEED_RESTART を確かめ、立っていれば DIF_PROPERTYCHANGE で動かし直す
- 直した後の実機: ロックで HidUsb まで **2.0 秒**、解除で WINUSB まで **2.6 秒**。ロック中のポインター・クリック、
  解除後の 3 本指ジェスチャーとも動いた（ユーザー確認）。マルチタッチ形式に切り替えたままの機器でも、標準の HID で問題なく動く
- 再起動（2026-11-16 20:49）: シャットダウン前（PRESHUTDOWN）の切り替えは、64 秒待たされた末に
  0xE0000223（ERROR_NO_CONFIGMGR_SERVICES）で失敗し、再起動を約 1 分遅らせた。シャットダウン中の PnP は
  ドライバーの導入を受け付けない。WinUSB のまま起動したが、サービスが開始時（起動の約 15 秒後）に気づいて 5.0 秒で HidUsb にし、
  ログオン画面で使えた（ユーザー確認）。ログオン後 2.1 秒で WINUSB に戻った
  - 対策: シャットダウン時の切り替えをやめ、起動時の切り替えだけにした（PRESHUTDOWN を受けない）
  - 再起動（21:09）: それでも再起動の途中のログオフで切り替えを始め、約 16 秒後に同じエラーで失敗した。
    起動時は 4.9 秒で HidUsb、ログオン後 1.6 秒で WINUSB。
    対策: ログオフの後は 5 秒待ち、その間に SERVICE_CONTROL_SHUTDOWN が来るか SM_SHUTTINGDOWN なら切り替えない
  - 再起動（21:18）: SHUTDOWN の知らせはログオフの 17 秒後で、5 秒の待ちでは足りず切り替えを始めた。
    ただし知らせと同時に失敗して終わり、シャットダウンは遅れなかった（ユーザー確認）。SM_SHUTTINGDOWN はセッション 0 では立たない
- インストーラーは「ログオン時の起動」（HKCU Run の MTP Agent）を登録していなかった（取り除くと消え、再導入で戻らない）。
  「ログオンしたら常駐アプリを自動で起動する」を追加した（既定でオン）
- ログオンから常駐アプリの起動まで 46 秒かかった。Shell-Core の記録（9705〜9708）では、Run の登録を 1 つずつ順に起動しており、
  OneDrive.Sync.Service に 16 秒、KeePassXC に 8 秒かかって、MTP Agent は最後だった。
  対策: サービスが WTS_SESSION_LOGON で WTSQueryUserToken → (UIAccess 版なら TokenUIAccess を付けて) CreateProcessAsUser で起動する

## 慣性スクロールとピンチ（2026-11-17）

- 慣性: 2 本指スクロールの最近 4 フレームの平均速度（ホイール単位/秒）が 800 以上で、離す前に 33ms 以上止まっていなければ開始。
  常駐アプリの別スレッドが約 8ms ごとに v0·e^(-t/τ)（τ 既定 400ms）を積分して送る。触れたら止める
- ピンチ: 間隔の変化が 250 単位以上かつ中心の移動量以上でピンチ、中心が先に 300 単位動けばスクロールに確定。
  量は 350 × ln(間隔の比) を Ctrl + ホイールで送る（Ctrl はピンチの間だけ押したまま）
- 2 本指の動作の後は、すべての指が離れるまでポインターを動かさない
- 実機: 慣性・ピンチとも既定値のまま問題なし（ユーザー確認）

## Bluetooth: SDP キャッシュの HID 記述子を書き換える方法（2026-11-18）

カーネルドライバーを使わずに Bluetooth でマルチタッチを取れないかを確かめた。結論は「切り替えと受け取りはできるが、
指 1 本ぶんの長さのレポートしか届かないので、ジェスチャーには使えない」。道具は `probe/bt_sdp.py`・`bt_mt_test.py`・`bt_mt_probe2.py`。

- Windows はペアリングした機器の SDP の記録を `HKLM\SYSTEM\CurrentControlSet\Services\BTHPORT\Parameters\Devices\<アドレス>\CachedServices`
  に REG_BINARY で保存している（SDP の data element の並びそのもの。手元の 22 件で、読んで組み立て直すと元と一致した）。
  Administrators が書ける。Magic Trackpad の HID 記述子（属性 0x0206、135 バイト）は、Windows が見せているコレクション
  （マウスの 0x02・0x55、ベンダー定義の 0x90）とまったく同じだった
- 記述子にベンダー定義のコレクション（UsagePage 0xFF31。入力 0x31、フィーチャー 0xF1、出力・フィーチャー 0xF2）を足して書き込み、
  - Bluetooth をつなぎ直すと、Windows が機器から SDP を取り直してキャッシュを上書きし、効かなかった
  - HID 機器だけを再起動する（`pnputil /restart-device BTHENUM\{00001124-...}`）と、書き換えた記述子が使われ、Col03（0xFF31）が現れた。
    hidbth は機器の起動のたびに、キャッシュから記述子を読んでいる
- Col03 にフィーチャー `F1 02 01` を送れた（以前は記述子にないため ERROR_INVALID_FUNCTION）。送るとポインターが止まり、
  マルチタッチのモードに切り替わる。モードは HID 機器を再起動しても続くが、トラックパッドが休止してつなぎ直すと戻る（送り直せば再び切り替わる）
- 入力 0x31 の届き方は、宣言した長さとの関係で決まる（hidclass が長さの合わないレポートを捨てる）
  - 111 バイト（指 12 本ぶん）で宣言: 1 件も届かない
  - 12 バイト（見出し 3 + 指 1 本 9）で宣言: 1 本指の間は毎秒 90 件届く。2 本指の間はほぼ届かない（切り詰めて通すこともしない）
  - レポートの中身は、2〜3 バイト目が 1 件ごとに 0x58 増える時刻、その後に指 1 本 9 バイト（USB の指のデータと同じ形に見える）
- GET_REPORT（HidD_GetInputReport、0x31）は、宣言どおりの長さでも ERROR_INVALID_PARAMETER（1 回約 22 ms。機器が断っている）
- レポート ID 1 つにつき宣言できる長さは 1 つで、トラックパッドは指の本数で長さを変える（3 + 9×本数）。
  そのため、この方法では複数の指を同時に受け取れない。Bluetooth でジェスチャーまで扱うには、カーネルドライバーか、
  専用の USB Bluetooth ドングルを WinUSB で直接扱うユーザーモードの Bluetooth スタック（Google Bumble など）が要る

## Bluetooth: MtpBth スパイクドライバーの実機確認（2026-11-18）

テスト署名モード（Secure Boot オフ、`bcdedit /set testsigning on`）で、`drivers\spike.ps1 install` により MtpBth を
Magic Trackpad（Lightning、PID 0265）の BTHENUM HID PDO に当て、`mtpdump --hex` で確かめた。**指の本数によらず、0x31 が全部届いた。**

- `link=connected last=0x00000000 attempts=1 handshake=0x0`。HID の L2CAP 通信路（PSM 0x11/0x13）を 1 回で開けて、
  マルチタッチへの切り替え（SET_REPORT Feature `F1 02 01`）も受け入れられた
- メモリ整合性（HVCI）がオンのままでも、ドライバーは読み込まれた
- 入力 0x31 は 3 + 9×本数 バイト（ID を含めると 13・22 バイト）。core の `MtpParseReport(MTP_TRANSPORT_BT, …)` で
  そのまま解析でき、指の ID・座標・圧力・状態（st 0→1→2→3→0）が USB と同じ形で取れた。1 件ごとに 2〜3 バイト目が 0x58 増える
- 押し込み（クリック）は見出しの 2 バイト目の最下位ビット（`btn=1`）に出る。Force Touch に使う圧力（p）も届いた
- `recv=743 delivered=602 dropped=141`: 読み取り要求が待っていない間に届いたレポートは捨てている（mtpdump の起動前の分を含む）。
  常駐アプリから使うときは、読み取りを複数重ねるか、ドライバーに小さな受け取り用の待ち行列を持たせる
- 入れている間、トラックパッドは Windows のマウスとして動かない（hidbth と入れ替わるため）

## Bluetooth: MtpBth での振動（2026-11-18）

MtpBth に `MTP_IOCTL_SET_REPORT` を足し、`mtpdump --haptic` で Bluetooth 用の振動レポート
（`F2 53 01 s0 78 02 s1 24 30 06 01 s2 18 48 12`、強さ 0x30）を 3 通りの送り方で送った（PID 0265）。
**振動したのは割り込みチャネルの DATA(Output)（HIDP ヘッダー 0xA2）だけ。**

| 送り方 | 結果 |
|---|---|
| 制御チャネル SET_REPORT(Feature)（0x53） | HANDSHAKE 成功（0x0）だが振動しない |
| 制御チャネル SET_REPORT(Output)（0x52） | HANDSHAKE 0x2（ERR_INVALID_REPORT_ID）で拒否 |
| 割り込みチャネル DATA(Output)（0xA2） | 振動した（割り込みチャネルには応答がない） |

- 常駐アプリ（`agent/mtp_haptic_out.c`）は割り込みチャネルに決め打ちした。HANDSHAKE が成功でも振動するとは限らないので、
  応答で送り方を選ぶ方法は使えない
- 管理者権限なしの mtpdump で MtpBth を読み書きで開けた（INF の `Security`（IU に GRGW）が効いている）
- 再接続直後は `last=0xC00000B5`（STATUS_IO_TIMEOUT）で `connecting` が続いた。トラックパッドをクリックして起こすと、
  3 秒おきのつなぎ直しで `connected` になった（attempts=8）

## Bluetooth: ロック中に Windows 標準の HidBth へ戻す（2026-11-18）

MagitraSwitch サービス（agent/mtp_switch.c）が、MtpBth を入れているときだけ Bluetooth のトラックパッドも切り替えるようにした。
ロックで MtpBth → HidBth、解除で HidBth → MtpBth。

- 切り替えの時間: 手動（mtpswitch）で 1.5 秒・1.7 秒、ロック・解除で 1.6〜2.2 秒・2.0〜6.1 秒（USB の約 8 秒より速い）
- 切り替えると L2CAP の通信路が切れるので、標準のドライバーで動き出すには、トラックパッドを 1 回クリックしてつなぎ直す必要がある。
  このクリックは Windows に届かない。ロック画面の最初の画面（時計）ではポインターが出ないので、何も動かないように見える。
  キーを押してパスワードの画面に進めてからクリックすると、ポインターが動いた
- `F1 02 00`（SET_REPORT Feature）で、マルチタッチ（入力 0x31）からマウスのモード（入力 0x02、8 バイト。
  例 `02 00 00 FE 00 00 00 01`）に戻ることを `mtpdump --hex --send 3 F10200` で確かめた。
  マルチタッチのまま HidBth に渡すと 0x31 を送り続けるおそれがあるので、MtpBth は外れる前（D0Exit）にこれを送る。
  これを入れる前は、ロック中にトラックパッドの電源を入れ直すまで動かなかったことがある（時計の画面のせいだったかは切り分けていない）
